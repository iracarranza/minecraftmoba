# The HUD layer — scope

**Status:** Working. Scoped, not built.
**Supersedes:** a belief recorded in `Hud.java`, quoted below.

---

## The correction this starts from

`Hud.java` currently says:

> Position stays fixed to the bossbar strip and the sidebar column, **which
> is the limit that remains real.**

That is wrong, and it has been shaping every HUD decision in this project —
including why `VitalsDisplay` draws at the top of the screen and why the
ability-refusal messages were sent to the action bar.

`toxicity188/BetterHud` is a shipping, multiplatform, server-side HUD that
"combines Minecraft's boss bar rendering with automatic resource pack
generation", and exposes per-element `align`, `x`, `y`, `scale` and
`render-scale`. So arbitrary screen placement from a bossbar is not only
possible, it is a solved production technique.

**What is actually fixed is the bossbar's LINE. What is free is where a glyph
sits relative to that line**, and the freedom is bought in the font, not in the
bossbar API.

> The bossbar stops being a bar and becomes a line of text we own.

Note the sibling project the technique was found through is *not* the one to
copy: `BetterHealthBar3` renders health above **entities** via virtual
TextDisplays and core shaders — a world-space problem — and targets
1.19.4-1.21.4 against our 1.21.11.

---

## The two mechanisms, both already built here

| Axis | Mechanism | State in this repo |
| --- | --- | --- |
| Horizontal | negative-space font, `U+F000+n` advances `-n` | **built**, `build_pack.py:259`, range 1..256 |
| Vertical | bitmap provider `ascent` | **built**, `glyph_ascent: 12` |
| Scale | bitmap provider `height` scales the source texture | **built**, `bars.height` |

Nothing new has to be invented. What is missing is that these are currently
hard-coded per glyph family rather than being properties of a *placed element*.

---

## The structural constraint, which decides the whole design

> **`ascent` and `height` belong to a font PROVIDER, not to an emission.**

A negative-space prefix can differ per emission, so `x` is free and continuous.
`y` and `scale` are not: every distinct `(y, scale)` pair needs its **own
provider entry** pointing at the same texture.

So the layout model is **declared layers, not free coordinates**. A layout with
four vertical positions costs four providers per glyph family it draws there.
That is cheap in bytes and not cheap in cardinality, and it is the thing that
would quietly explode if elements were given continuous `y`.

**Consequence for config:** `y` and `scale` are enumerated in the pack registry
and referenced by name from the plugin. `x` is a number the plugin computes at
send time.

### Baseline drift between bossbars

Each bossbar is its own line with its own baseline, and they stack downward.
An element with a given `ascent` therefore lands in a different place depending
on **which bossbar it was drawn in**.

This project already shows four: `HungerDisplay`, `InWorldSelection`,
`Rewards`, `VitalsDisplay`. A layer's absolute position is
`bossbar_index_offset + ascent`, so either the layer table records which
bossbar it assumes, or one bossbar is nominated as the canvas and everything
draws in it.

**Recommended: one canvas bossbar.** Multiple bossbars then serve only as extra
independent lines when something genuinely needs to update at a different
cadence, and the common case has no drift to reason about.

## What ships

### 1. Transparent bossbar sprites

`assets/minecraft/textures/gui/sprites/boss_bar/` — 22 files, six colours x
`{colour}_background` / `{colour}_progress`, plus the notched variants
(`notched_6`, `notched_10`, `notched_12`, `notched_20`).

Written fully transparent so the coloured bar disappears and only the title
renders. Generated by `build_pack.py` like everything else, not committed as
binaries.

**Reserve at least one colour undisguised.** Something will eventually want a
real progress bar, and having blanked all seven is a decision that is annoying
to reverse. `PURPLE` is unused by any current caller.

### 2. A layer table in `registry.json`

```
layers:
  hotbar_above:   { ascent: 22, height: 16 }
  hotbar_above_2: { ascent: 32, height: 16 }
  abilities_over: { ascent: 40, height: 16 }
```

Each layer, crossed with each glyph family that draws in it, emits one provider.
The build refuses `ascent > height` rather than shipping a pack the client will
reject.

### 3. `HudLayer` in the plugin

Pure arithmetic, no Bukkit: takes a layer name and an `x` in pixels, returns the
codepoint prefix (negative space) and the glyph base for that layer. Tested
without a server, exactly as `VitalsBar` is.

### 4. First two consumers

- **Vitals moved to `hotbar_above`.** `VitalsBar` already builds its runs; only
  the placement changes.
- **The ability-refusal line at `abilities_over`**, owning *not unlocked*,
  *still on cooldown* and *cannot be used right now*.

That second one is the real prize. It flashes illegibly today because the
action bar has **twenty-six call sites across thirteen files** with no arbiter.
This routes around that surface instead of building an arbiter for it — the
refactor is still worth doing on its own merits, and is no longer blocking.

## Risks

- **No pack, no HUD.** Unmapped codepoints render as tofu. Everything stays
  behind `features.vitalsBar.enabled` and degrades to `Hud`'s plain-text
  baseline, which exists for this.
- **Clipping at extreme ascent** is unmeasured. Step 1 exists to find it.
- **Provider cardinality** grows as layers x families. Fine at the scale here;
  worth watching if layers ever become per-element.
- **Do not adopt BetterHud itself.** It is premium, it is a general-purpose
  YAML HUD engine, and it would put a second pack generator in competition with
  `build_pack.py` over the same font namespace. Take the technique and the API
  shape; leave the dependency.

## Open

- Whether `scale` wants independent x/y, as BetterHud's `render-scale` has.
